The Client Scenario

ℹ️

Setting the Scene

It's 11pm on a Friday. A security analyst at one of your financial services clients spots something suspicious in the logs — a phishing email that may have compromised two employee accounts. She types into the internal support chat:

"We received a phishing email from our own domain. Two employees may have clicked the link. Possible credential compromise."

Today, that message sits in a queue until Monday morning. A Level-1 agent reads it, recognises it's urgent, and manually escalates it to the security team. By the time anyone acts, 60 hours have passed.

With the application you're building today: that description is classified as a Security Incident at 96% confidence, routed to the SOC, assigned a ticket ID, and the team is notified — in under 3 seconds, at any hour.

Where to Take This Next

You've built a working, deployed classifier. These three extensions turn it into a production-grade service — and each one represents a natural scope of work to bring back to a client. Bob can generate the code for all three.

01

Upgrade to IBM watsonx.ai Classification

Replace the keyword matching in ticket_classifier.py with a call to IBM Granite. The model reads the description and returns the classification — far more accurate on ambiguous or conversational inputs. The API interface doesn't change at all.

Ask Bob:
"Replace the keyword classification logic in ticket_classifier.py with an IBM watsonx.ai Granite model API call. Keep the same TicketResult output format."

Easy — one function, one watsonx.ai API key
02

Route to ServiceNow, Jira, or Slack

After classification, add a requests.post() call to create a real ticket in the client's existing system. CRITICAL tickets go directly to a Slack or Teams channel. The ticket ID returned becomes the actual ServiceNow or Jira number.

Ask Bob:
"After classification, add a Slack webhook notification for CRITICAL tickets and a ServiceNow REST API call to create the ticket for all other priorities."

Medium — one OAuth token per downstream system
03

Connect to watsonx Orchestrate

Register your deployed Code Engine URL as an HTTP tool in a watsonx Orchestrate agent. When an employee describes a problem to the Orchestrate agent, it calls your endpoint automatically and confirms the ticket and SLA in the same conversation.

Ask Bob:
"My ticket classifier is live at [your Code Engine URL]. Show me how to register it as an HTTP tool in a watsonx Orchestrate agent YAML."

Advanced — requires a watsonx Orchestrate instance

The Full Architecture

Here is the end-to-end system you can describe and demo to any enterprise client after today:

  Employee describes their problem in plain English
            ↓
  watsonx Orchestrate agent receives the message
            ↓
  Agent calls POST /classify on your Code Engine endpoint
            ↓
  ticket_classifier.py runs in under 1 second:
    • Classifies issue type with confidence score
    • Extracts systems, amounts, and error codes from the text
    • Applies routing rules → team, priority, SLA
            ↓
  Returns structured JSON with ticket ID, team, SLA, next steps
            ↓
  [Extension 01] IBM Granite makes the classification smarter
  [Extension 02] ServiceNow / Jira ticket created · Slack alert sent
  [Extension 03] Orchestrate agent confirms everything in the conversation
            ↓
  Employee has a ticket number and SLA in under 3 seconds
  The right team has it before the employee finishes reading the confirmation
